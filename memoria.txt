MEMORIA DE LA PRÁCTICA

1. INTRODUCCIÓN

En esta práctica se ha desarrollado un sistema de almacenamiento de documentos compartidos basado en una arquitectura de microservicios. La solución está dividida en dos servicios independientes: el servicio de usuarios, encargado de gestionar registros, autenticación y tokens, y el servicio de ficheros, encargado de almacenar y controlar el acceso a los documentos de cada usuario.

La aplicación se implementa con Quart, un framework ASGI para Python, y se despliega mediante contenedores Docker usando docker-compose. El objetivo principal es crear una API REST funcional, segura y modular, en la que cada servicio puede gestionarse y escalarse de forma independiente.


2. OBJETIVOS DE LA PRÁCTICA

Los objetivos docentes de esta práctica son los siguientes:
- Desarrollar microservicios en Python con una API REST.
- Gestionar autenticación mediante tokens y validación de acceso.
- Diseñar un sistema de almacenamiento basado en directorios por usuario.
- Implementar persistencia local en archivos JSON y texto.
- Utilizar Docker y docker-compose para desplegar los servicios.
- Crear un cliente de pruebas para verificar el comportamiento de todas las rutas.


3. ARQUITECTURA DE LA SOLUCIÓN

La práctica se estructura en dos microservicios principales:

3.1 Servicio de usuarios
Este servicio gestiona la creación, autenticación y modificación de usuarios. Cada usuario se identifica con un UID generado aleatoriamente y se le asigna un token de acceso calculado a partir de un UUID secreto compartido entre los servicios.

Funciones implementadas:
- PUT /user: creación de un usuario con nombre y contraseña.
- POST /user: login del usuario y obtención de token.
- PATCH /user: cambio de contraseña del usuario autenticado.

La contraseña no se almacena en texto plano; se preserva mediante un hash SHA-256.

3.2 Servicio de ficheros
Este servicio gestiona el directorio de documentos de cada usuario. Cada UID corresponde a un directorio físico, dentro del cual se guardan los archivos de texto. Además, el servicio mantiene metadatos para indicar si un documento es público o privado.

Funciones implementadas:
- GET /file/<uid>: listar documentos del usuario autenticado.
- PUT /file/<uid>/<filename>: crear o actualizar un documento.
- GET /file/<uid>/<filename>: recuperar un documento.
- DELETE /file/<uid>/<filename>: eliminar un documento.
- PATCH /file/<uid>/<filename>: cambiar la visibilidad del documento.

El servicio de ficheros valida el token de autenticación en la cabecera Authorization con el formato Bearer <token>.

3.3 Cliente de pruebas
El cliente de pruebas se ha desarrollado en Python con la librería requests. Su función es lanzar una batería de peticiones para comprobar que todos los endpoints funcionan correctamente, incluyendo los escenarios de error esperados.


4. DISEÑO E IMPLEMENTACIÓN

4.1 Generación de UID y tokens
Para asegurar la identidad de los usuarios, se emplea UUID v4 para generar un identificador único por usuario. El token de acceso se genera con uuid.uuid5 usando un UUID secreto compartido por ambos servicios. Esto permite verificar que un usuario pueda acceder solamente a su propio directorio y evita que otros usuarios no autorizados puedan operar sobre recursos ajenos.

4.2 Almacenamiento de usuarios
La información del usuario se guarda en un archivo JSON dentro del volumen persistente del servicio. En cada registro se conserva:
- nombre de usuario
- UID
- contraseña en formato hash

Esto permite que la información pueda recuperarse tras reiniciar el contenedor sin perder el estado del servicio.

4.3 Almacenamiento de documentos
Cada usuario tiene un directorio identificado por su UID. Dentro de dicho directorio se almacenan los archivos de texto. Además, el sistema usa un archivo metadata.json para guardar la visibilidad pública o privada de cada documento.

4.4 Seguridad y validación
Las principales decisiones de seguridad son:
- Las contraseñas nunca se guardan en claro.
- Los tokens se validan en cada petición que requiera autenticación.
- Un usuario solo puede acceder a su propio directorio.
- Los documentos privados solo pueden leerse por su propietario.
- Los documentos públicos pueden consultarse sin autenticación si se conoce el UID y el nombre del archivo.

4.5 Docker y despliegue
Se usa docker-compose para levantar los servicios en contenedores separados, cada uno con su propio puerto y volumen de persistencia. Esto facilita el aislamiento de la lógica, la reutilización del mismo proyecto y la fácil ejecución del sistema en un entorno reproducible.


5. ENDPOINTS Y COMPORTAMIENTO

Servicio de usuarios:
- PUT /user
  Descripción: crear usuario.
  Entrada: JSON con name y password.
  Salida: UID y token.

- POST /user
  Descripción: iniciar sesión.
  Entrada: JSON con name y password.
  Salida: UID y token.

- PATCH /user
  Descripción: modificar la contraseña.
  Entrada: JSON con password.
  Requiere: cabecera Authorization: Bearer <token>.

Servicio de ficheros:
- GET /file/<uid>
  Descripción: listar documentos del usuario.
  Requiere autenticación.

- PUT /file/<uid>/<filename>
  Descripción: crear o actualizar documento.
  Requiere autenticación.

- GET /file/<uid>/<filename>
  Descripción: recuperar el contenido de un archivo.
  Si es público, permite acceso sin autenticación; si es privado, hace falta autenticación.

- DELETE /file/<uid>/<filename>
  Descripción: eliminar documento.
  Requiere autenticación.

- PATCH /file/<uid>/<filename>
  Descripción: cambiar visibilidad pública/privada.
  Requiere autenticación.

7. JUSTIFICAR DECISIONES DE DISEÑO

La decisión principal de diseño ha sido separar la lógica en dos microservicios distintos. Esta estructura permite mantener una clara división de responsabilidades:
- el servicio de usuarios se encarga de identidad y autenticación,
- el servicio de archivos se encarga de la gestión del almacenamiento.

También se ha optado por una persistencia sencilla basada en archivos JSON y directorios de texto, ya que es suficiente para un prototipo funcional y facilita la explicación, depuración y pruebas de la práctica. La gestión de metadatos por documento permite controlar con facilidad la propiedad y la visibilidad sin introducir complejidad innecesaria.

La validación de tokens en cada petición restringe el acceso a recursos no autorizados. Este planteamiento refleja un diseño seguro y transparente, compatible con los requisitos del enunciado y con la filosofía de los microservicios.

Además, el uso de Docker y docker-compose permite reproducir el entorno completo con un único comando, favoreciendo la ejecución del sistema en cualquier máquina con Docker instalado. Esto simplifica la evaluación y el despliegue del proyecto.


8. CONCLUSIONES

La práctica ha permitido poner en práctica los conceptos de API REST, autenticación basada en tokens, serialización JSON y despliegue en contenedores. El resultado es un sistema funcional que cumple con los objetivos de la asignatura: gestión de usuarios, protección del acceso a documentos y despliegue de servicios de forma aislada.

La solución desarrollada demuestra la utilidad de los microservicios para separar responsabilidades y facilitar la evolución del sistema. En un escenario real, podría ampliarse con mecanismos de autenticación más seguros, como JWT con expiración y firma criptográfica, así como con mejor gestión de permisos y almacenamiento persistente en bases de datos.
