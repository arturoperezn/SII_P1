  #### 1.1. Responsabilidad y Arquitectura del Servicio

  • Propósito: Gestión de identidades, autenticación y emisión de credenciales de acceso
  (UID y tokens).
  • Framework: Mencionar el uso de Quart como framework ASGI asíncrono en Python,
  escuchando en el puerto 5050.

  #### 1.2. Generación de UIDs y Tokens (El secreto compartido)

  • UID de usuario: Se genera con uuid.uuid4() para garantizar un identificador único y
  no predecible para cada usuario.
  • Token de acceso: Se deriva mediante uuid.uuid5(UUID(secret_uuid), user_uid) usando el
  espacio de nombres de un UUID secreto.
  • Comunicación sin acoplamiento: Explica que el archivo secret_uuid.txt se aloja en el
  volumen compartido /app/shared_data. Esto permite que el servicio file.py valide tokens
  de forma autónoma sin necesidad de consultar por red a user.py en cada petición.
  • Nota de seguridad: Mencionar que, aunque este mecanismo determinista cumple con los
  requisitos didácticos, en producción se usarían esquemas como JWT firmados con clave
  asimétrica y tiempo de expiración.

  #### 1.3. Seguridad y Persistencia de Datos

  • Almacenamiento: Persistencia local en formato JSON en /app/data/users.json (montado
  en el volumen persistente data_users).
  • Protección de contraseñas: Justificar que las contraseñas nunca se guardan en texto
  claro; se procesan mediante hash_pwd() utilizando un algoritmo seguro unidireccional
  (SHA-256 con hexdigest()).
  • Estructura del registro: Explicar la estructura almacenada en memoria y disco:
    {
      "alicia": {
        "uid": "e7b0c3a2-...",
        "pwd_hash": "5e884898da28..."
      }
    }


  #### 1.4. Endpoints y Tratamiento de Errores

  Detalla cada endpoint implementado mediante una breve tabla o lista explicativa:

  • PUT /user (Registro de usuario):
      • Entrada: JSON {"name": "...", "password": "..."}.
      • Validaciones: Devuelve 400 Bad Request si faltan parámetros o cuerpo; 409
      Conflict si el nombre de usuario ya existe.
      • Éxito: Genera UID, hash y token, persiste en disco y devuelve 201 Created con {
      "uid": "...", "token": "..." }.
  • POST /user (Inicio de sesión / Login):
      • Entrada: JSON {"name": "...", "password": "..."}.
      • Validaciones: 400 Bad Request si faltan datos; 404 Not Found si el usuario no
      existe; 401 Unauthorized si la contraseña no coincide con el hash.
      • Éxito: Devuelve 200 OK con { "uid": "...", "token": "..." }.
  • PATCH /user (Modificación de contraseña):
      • Autenticación: Requiere la cabecera Authorization: Bearer <token>. La función
      auxiliar check_login() busca el usuario que generó dicho token. Si no es válido ->
      401 Unauthorized.
      • Validaciones: 400 Bad Request si falta el nuevo campo password.
      • Éxito: Actualiza el hash de la contraseña en users.json y responde 200 OK.

  ### 2. Apartado: Batería de Pruebas y Validación (cliente.py)

  La rúbrica califica el cliente con 2 puntos y exige que sea no interactivo,
  automatizado con la librería requests y que compruebe tanto los casos de éxito como los
  casos de error.

  #### 2.1. Metodología y Estructura del Cliente

  • Automatización: Explicar que el script ejecuta una secuencia de peticiones HTTP
  contra ambos microservicios sin intervención manual.
  • Mecanismo de validación (probar()):
      • Detalla cómo funciona la función auxiliar probar(nombre_prueba, respuesta,
      codigo_esperado):
          • Comprueba si el código HTTP devuelto coincide exactamente con el esperado.
          • Muestra un mensaje verde/limpio [OK] en caso de éxito.
          • En caso de fallo ([FAIL]), imprime el código recibido y el cuerpo del error
          para facilitar la depuración.



  #### 2.2. Cobertura de Pruebas Implementadas

  Organiza la explicación de las pruebas en dos grandes bloques:

  1. Casos de Éxito (Happy Path):
      • Creación de usuario Alicia (PUT /user → 201).
      • Inicio de sesión (POST /user → 200).
      • Subida de documento privado (PUT /file/<uid>/doc.txt → 200).
      • Lectura de documento privado por su propietario con token (GET /file/<uid>/doc.
      txt → 200).
      • Modificación de visibilidad a público (PATCH /file/<uid>/doc.txt → 200).
      • Lectura de documento público sin token (GET /file/<uid>/doc.txt → 200).
      • Listado de documentos del usuario (GET /file/<uid> → 200).
      • Eliminación de documento (DELETE /file/<uid>/doc.txt → 200).
  2. Casos de Error y Control de Excepciones (Edge Cases):
      • Parámetros faltantes o inválidos: Envío de JSON incompleto a /user (400 Bad
      Request).
      • Conflicto de unicidad: Reintentar registrar un usuario existente (409 Conflict).
      • Credenciales incorrectas: Login con contraseña errónea (401 Unauthorized) o
      usuario inexistente (404 Not Found).
      • Acceso no autorizado: Intentar leer un archivo privado sin token (401
      Unauthorized) o con el token de otro usuario distinto.
      • Recurso inexistente: Intentar recuperar o borrar un archivo que no existe (404
      Not Found).
